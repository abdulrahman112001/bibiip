# لوحة تحكم الأدمن 🐝

لوحة تحكم كاملة للتحكم في **كل** محتوى الموقع (نصوص، صور، أرقام...) من غير
ما تلمس كود خالص — كل حاجة بتتحفظ في قاعدة بيانات وتبان في الموقع فورًا.

---

## 1) تسجيل الدخول

الرابط: `http://localhost:3000/admin` (أو `https://your-domain.com/admin` بعد النشر)

بيانات الدخول الحالية موجودة في ملف `.env`:

```
ADMIN_EMAIL="admin"
ADMIN_PASSWORD_HASH="\$2b\$10\$..."
```

**عشان تغيّر كلمة السر:**

```bash
node -e "console.log(require('bcryptjs').hashSync('كلمة السر الجديدة', 10).replaceAll('$','\\$'))"
```

انسخ الناتج وحطه بدل `ADMIN_PASSWORD_HASH` في `.env`.

> ⚠️ **مهم جدًا:** لازم كل علامة `$` في الهاش تتكتب `\$` (مش `$` عادي).
> السبب: Next.js بيعمل "variable expansion" لأي `$شيء` جوا ملفات `.env`
> (زي `$HOST` أو `$PORT`)، وهاش bcrypt مليان علامات `$` بطبيعته، فلو
> كتبتها من غير escape، Next.js هيفهمها غلط ويقطع الهاش من غير أي خطأ
> واضح — تسجيل الدخول هيفشل بصمت ("الإيميل أو كلمة السر غلط") مع إن
> البيانات صح فعليًا. الأمر اللي فوق بيعمل الـ escape أوتوماتيك.

## 2) إزاي شغالة (Architecture)

```
قاعدة البيانات (جدول ContentSection: key + data JSON)
        ↑ يتحدّث بـ PUT من الداشبورد
        ↓ يتقرا بـ getContent() في page.tsx (Server Component)
الموقع العام (كل سكشن بياخد الداتا كـ prop)
```

- **كل سكشن في الموقع = صف واحد في قاعدة البيانات**، مفتاحه نفس اسم الـ
  export في [content.ts](../src/lib/content.ts) (`hero`, `services`, ...).
  المحتوى بالكامل (بما فيه كل نصوص `{en, ar}`) متخزن كـ JSON مرن، مش
  أعمدة SQL جامدة — عشان أي تعديل مستقبلي على شكل المحتوى ميحتاجش
  migration جديدة.
- **`src/lib/getContent.ts`**: بيجيب سكشن من قاعدة البيانات، ولو مش لاقيه
  (أو قاعدة البيانات مش شغالة لأي سبب) بيرجع نسخة `content.ts` الثابتة
  كـ fallback — الموقع مايوقفش أبدًا حتى لو حصلت مشكلة في الاتصال.
- **`src/lib/contentSchemas.ts`**: وصف شكل كل سكشن (مش القيم) — بيستخدمه
  محرّك الفورم العام في الداشبورد (`SectionForm` + `FieldRenderer`) عشان
  يرسم الحقول المناسبة (نص ثنائي اللغة، صورة، رقم، مصفوفة قابلة للتعديل...)
  من غير ما نكتب فورم مخصص لكل سكشن.
- **المصادقة**: Auth.js (NextAuth v5)، أدمن واحد بس، بياناته في `.env`
  (مفيش جدول مستخدمين — مش محتاجينه لأدمن واحد). `src/proxy.ts` بيحمي كل
  `/admin/*` و `/api/admin/*`.
- **الصور**: أي حقل صورة في الداشبورد فيه زرار "ارفع صورة" حقيقي — بيرفع
  الملف ويتخزن كـ bytes جوا قاعدة البيانات نفسها (موديل `Asset`)، وبيتعرض
  عن طريق `/api/assets/[id]`. ده بيشتغل صح محليًا وبعد النشر من غير ما
  نحتاج خدمة تخزين ملفات خارجية (زي S3/Vercel Blob). ارفع صورة جديدة على
  أي حقل (حتى لو كان فيه صورة قديمة من `public/brand`) وهي هتحل محلها
  أوتوماتيك. الحد الأقصى للحجم 5 ميجا.

> ⚠️ **ملحوظة تطوير محلي**: لو شغّلت سكريبت منفصل (زي `tsx`) بيفتح اتصال
> بقاعدة البيانات (`dev.db`) في نفس الوقت اللي السيرفر (`npm run dev`)
> شغال فيه، ممكن يحصل تعارض قفل SQLite (السكريبت يعلّق أو يرجّع بيانات
> قديمة). اقفل السيرفر الأول لو محتاج تشغّل سكريبت مباشر على القاعدة.
> المشكلة دي بتختفي تمامًا لما تنتقل لـ Postgres في الإنتاج (بيدعم
> اتصالات متعددة بطبيعته).

## 3) الـ APIs

| الطريقة | الرابط | الوصف | يحتاج تسجيل دخول؟ |
|---|---|---|---|
| GET | `/api/content` | كل سكاشن الموقع دفعة واحدة | ❌ عام |
| GET | `/api/content/[key]` | سكشن واحد | ❌ عام |
| GET | `/api/admin/content` | قايمة كل السكاشن + آخر تعديل | ✅ |
| GET | `/api/admin/content/[key]` | القيمة الحالية لسكشن (للتعديل) | ✅ |
| PUT | `/api/admin/content/[key]` | حفظ نسخة جديدة من سكشن | ✅ |
| POST | `/api/admin/assets` | رفع صورة جديدة (بيرجع `{ url }`) | ✅ |
| GET | `/api/assets/[id]` | عرض صورة مرفوعة | ❌ عام |

مثال استخدام خارجي (لو حبيت تجيب المحتوى من مكان تاني):

```bash
curl https://your-domain.com/api/content/services
```

## 4) إضافة سكشن جديد

1. ضيف الـ export الجديد في [content.ts](../src/lib/content.ts) (بنفس
   شكل الباقي: `{ en, ar }` لأي نص).
2. ضيف وصف الحقول في [contentSchemas.ts](../src/lib/contentSchemas.ts)
   (نفس نمط اللي موجود).
3. ضيف اسمه في `sectionLabels` في نفس الملف.
4. شغّل `npm run db:seed` عشان يتضاف صف جديد في قاعدة البيانات.
5. غيّر الكومبوننت بتاعه ياخد المحتوى كـ `prop` بدل ما يستورده مباشرة من
   `content.ts` (زي باقي الكومبوننتس)، وضيفه في `page.tsx`.

## 5) الانتقال لقاعدة بيانات حقيقية (Production)

دلوقتي شغالين بـ SQLite محلي (`dev.db`) — كويس للتطوير بس، مش هيشتغل على
Vercel (الملفات مؤقتة هناك). قبل النشر:

1. اعمل قاعدة بيانات Postgres (من Vercel Dashboard → Storage → Create
   Database → Postgres، أو أي مزوّد تاني زي Neon/Supabase).
2. حط الـ connection string في `DATABASE_URL` (في إعدادات Environment
   Variables بتاعة Vercel، أو `.env` محليًا).
3. في `prisma/schema.prisma`، غيّر `provider = "sqlite"` لـ
   `provider = "postgresql"`.
4. في `src/lib/prisma.ts`، بدّل `@prisma/adapter-libsql` بـ
   `@prisma/adapter-pg` (`npm install @prisma/adapter-pg`, `import { PrismaPg } from "@prisma/adapter-pg"`).
5. شغّل `npx prisma migrate deploy` عشان ينشئ الجداول على القاعدة الجديدة،
   وبعدين `npm run db:seed` عشان يملأها بالمحتوى الحالي.

كل باقي الكود (الداشبورد، الـ APIs، الموقع) هيفضل شغال زي ما هو من غير
أي تغيير.

## 6) تشغيل محلي

```bash
npm run dev          # التطوير
npm run db:seed       # (مرة واحدة) هجرة المحتوى من content.ts لقاعدة البيانات
npm run db:studio     # واجهة Prisma Studio لتصفح/تعديل قاعدة البيانات مباشرة
```
